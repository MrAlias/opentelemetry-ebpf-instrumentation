# ADR 001: Java remote-parent reverse transport

- Status: accepted for proof of concept
- Scope: inbound Java HTTP/1.1 remote-parent retrieval
- Related issues: `MrAlias/opentelemetry-ebpf-instrumentation#2` and native
  sub-issues `#9` through `#40`

## Context

OBI observes an upstream trace parent below TLS. An unmodified OpenTelemetry or
Splunk Java agent needs that parent synchronously, before its normal server
instrumenter starts a span. The Java process must not receive BPF map file
descriptors, bpffs access, BPF capabilities, or a path that uses
`bpf_probe_write_user`.

The reverse transport is only one part of correctness. Both transports look up
the same request-owned kernel state. If the current execution cannot be mapped
unambiguously to one generation, the result is a miss regardless of transport.

## Decision

Use optional `BPF_CGROUP_SETSOCKOPT` and `BPF_CGROUP_GETSOCKOPT` programs on
the actual application socket as the primary transport. Use a connected dummy
socket only to probe hook availability. Use a credential-checked Unix-domain-
socket request and response service owned by OBI as the fallback.

This intentionally supersedes issue #20's proposed cached dummy-socket data
path. A dummy socket can prove that the hooks are callable, but it does not own
the accepted connection. Take and discard therefore run on the backend's
actual accepted socket, allowing socket-local negotiation and the
kernel-derived tuple and network namespace to bind a claim to that connection.

The sockopt program lives in a separate BPF object. OBI probes program-type
support and loads/attaches that object independently, so an unsupported kernel
does not prevent OBI or Java TLS instrumentation from starting. The custom
level is `0x4f42`; `getsockopt` option `0x4a01` performs take and `0x4a02`
performs discard. `setsockopt` option `0x4a03` performs a non-consuming
capability negotiation with the exact process capability generated by OBI and
registered by the JVM. Negotiation is socket-local and becomes usable only
after the data hook acknowledges the kernel-derived tuple, network namespace,
and request generation. All unrelated levels and options retain normal kernel
behavior.

The primary program derives the current process, PID namespace, kernel thread,
mounted virtual thread, and generation-bound executor owner in the kernel. It
copies the fixed record through the sockopt context, not a user-memory helper.
Take and discard compete for one generation-specific claim-map entry shared by
both transports.

The fallback listens at `/var/run/obi/java-remote-parent.sock` by default with
mode `0660`, fixed framing, short read/write deadlines, bounded concurrent
handlers, and exact-path cleanup. Its real parent directory must be owned by
OBI, use the configured group, have mode `0750`, and not be a symlink. The Java
helper accepts only a socket at the configured path whose peer UID exactly
matches the OBI UID supplied at attach time. `SO_PEERCRED` is authoritative for
the client process at the server. `/proc` validation binds the requested
namespace TID to that process and derives the BPF map key. A version 2 request
also carries the unpredictable nonzero process capability generated by OBI at
attach time; the server compares it with both the exact authorization and the
JVM registration so PID reuse cannot authenticate a buffered request or stale
cache entry. The application never selects a PID. Successful thread lookups
are cached, but the process, thread, PID-namespace identity, authorization, and
registration are revalidated on every cache hit.

In `auto` mode, OBI selects sockopt when the separate object can be loaded and
both hooks can be attached; otherwise it starts the Unix service. The helper
probes the selected transport once, then negotiates the actual application
socket for each receive before caching that socket for a single take or
discard. It does not attempt both transports after a normal miss. Transport
errors trigger bounded reconfiguration rather than a request-path retry loop.

## Alternatives

| Candidate | Synchronous before span | Java privilege | Request identity | Restart/version behavior | Decision |
| --- | --- | --- | --- | --- | --- |
| Cgroup sockopt on accepted application socket | Yes | Ordinary socket syscall plus helper socket recovery | Kernel execution, socket-local negotiation, tuple, network namespace, and staged generation | Optional object and explicit ABI | Primary |
| Cgroup getsockopt on a dummy socket | Yes | Ordinary socket syscall | Kernel execution without accepted-connection ownership | Cannot bind authorization to the application connection | Reject as data path; probe only |
| Credential-checked Unix socket | Yes | Filesystem access to one local endpoint | Peer process plus validated logical TID | Reconnectable, explicit framing | Fallback |
| Brokered/pinned BPF map FD | Yes | Grants map access or file descriptor | Caller-controlled lookup | Difficult revocation | Reject |
| Direct bpffs lookup | Yes | Requires bpffs and BPF permissions | Caller-controlled lookup | Exposes internal ABI | Reject |
| Shared memory | Yes | Shared writable memory | Needs a second secure ownership protocol | Complex restart cleanup | Reject |
| Ring/perf buffer | No | None | Asynchronous notification races extraction | Natural OBI restart | Reject alone |
| Custom ioctl plus user-memory write | Potentially | Ordinary syscall | Current execution | Requires unsafe output mechanism | Reject |
| Process-level agent discovery | No per-request value | None | Identifies an agent, not a request | Useful only for capability discovery | Reject as carrier |

Asynchronous channels cannot guarantee that a record is available before the
server propagator runs. Process-level discovery proposals likewise do not carry
per-request trace context.

## Feature and fallback gates

Primary selection requires all of the following:

- `CGroupSockopt` program-type probing succeeds at runtime;
- the separate object loads and its internal pinned maps match the producer;
- OBI attaches both the set- and get-sockopt programs at the effective cgroup;
- the Java helper completes authenticated capability negotiation through the
  set-sockopt hook and receives the same capability from the get-sockopt
  health option on the connected probe socket.

The valid, missing, stale, and one-shot request cases are privileged acceptance
tests, not startup feature probes. Likewise, nested or competing cgroup
programs are deployment compatibility cases: the health exchange detects a
hook that blocks or rewrites the probe, but it cannot prove that no program at
another cgroup will affect a later application socket. Such topologies must be
tested explicitly and can select forced Unix mode when they are incompatible.

Failure of any gate selects the Unix fallback in `auto` mode and records one
bounded reason. Forced `getsockopt` reports unsupported instead of silently
falling back. Forced `unix` does not attempt the kernel hook. `disabled` leaves
existing OBI and Java-agent behavior unchanged.

The fallback requires a shared filesystem location, peer credentials, readable
peer `/proc` identity, and strict socket ownership/mode. Endpoint replacement,
malformed framing, unauthorized identity, overload, timeout, and restart all
return a non-valid status and fail open.

TCP senders retain the 26-byte legacy option while this bridge is disabled.
When enabled, they send the 27-byte version that adds exact trace flags. New
receivers accept both sizes, but only exact-flag candidates may enter the Java
bridge. A rolling deployment must therefore upgrade all receivers while the
bridge remains disabled, then enable it. Rollback disables the bridge before
downgrading receivers. Sending the 27-byte option to an old receiver is outside
the supported mixed-version sequence and can disconnect propagation.

## Security and limitations

The option pair is collision-resistant, not globally reserved. A program at a
nested cgroup can observe or override the same call. Runtime validation and the
forced fallback provide a diagnostic path, but deployments must attach OBI at
the Java workload's effective cgroup.

The Unix socket authenticates a process, while request ownership is still
proved by the staged logical execution identity. The configured group grants
connect access, not permission to replace the endpoint. Deployments with
different application and OBI groups must create the shared directory with the
configured GID before startup; the demo uses an explicitly initialized named
volume. A compromised instrumented JVM may consume its own record. A process
running as the OBI UID can impersonate this local fallback, so the OBI UID and
host root remain inside the trust boundary. The endpoint and diagnostics do
not reveal context identifiers.

Fallback connections have one absolute deadline, a shorter pre-authentication
read deadline, a per-peer cap, and a global cap shared by pre-authentication and
authenticated handling. Saturation returns `overload` without looking up or
consuming context. Multiple cooperating processes that already have connect
permission can still exhaust the bounded admission pool and temporarily deny
fallback service; group membership is therefore part of the availability trust
boundary. The primary transport and application request processing remain
fail-open, and this local denial-of-service risk is accepted for the PoC.

Connection-only correlation is insufficient for pipelined, coalesced, or
multiplexed requests. Ambiguous HTTP/1.1 inputs deliberately miss. HTTP/2 is
unsupported until a stream-safe identity exists.

Each accepted socket descriptor is stored in a fresh, one-shot Java holder.
Exact executor, ForkJoin, Netty, and virtual-thread task captures share that
holder with the generation-bound task token. Task entry masks any prior worker
binding, task exit restores it, and take or discard atomically consumes the
shared descriptor before transport readiness, buffer acquisition, or native
lookup. Cancellation and rejection detach the task without invalidating a
holder that another exact alias may still claim. This supports instrumented
task ownership across a TLS-receive-to-extraction thread change without
duplicating or retaining the application socket. Packaged-agent probes prove
the task-scope mechanism; a framework-specific pre-extraction claim still
requires retained privileged trace evidence.

The descriptor is only a lookup handle. Socket-local negotiation and the exact
task generation still authorize retrieval, so close or numeric descriptor
reuse can cause a miss but cannot select a newer connection's parent. A
framework handoff outside the instrumented task surfaces remains an explicit
primary-transport miss and never falls back to a dummy socket or a
connection-only guess.

## Rollout and evidence

The default is `disabled`. The proof-of-concept runner exercises `getsockopt`,
`unix`, and `disabled` independently and retains exact parent assertions,
transport counters, environment details, and the measurements selected by the
run mode. Results are recorded in
`examples/apache-java-https/.runtime/results/`; unexecuted matrix cells are
marked `untested`, never inferred from kernel version strings.

Rollback sets the transport to `disabled` and removes `obi` from the ordered
Java propagator list. Neither action requires a custom Java-agent build.
